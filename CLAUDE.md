## What this is

A **Feeding Report Manager** for a dog daycare/boarding operation. Staff use a tablet web app during a feeding session to log which dogs ate how much, plus medicine/supplements, by dragging dog cards into physical "pen" slots. On submit, the system emails-prefills a JotForm per dog and posts a review summary to a Telegram group; a human replies `/send` in Telegram and an n8n workflow pushes the staged data into JotForm.

There is **no build, test, or lint tooling** in the traditional sense — the sources are hand-edited files plus a changelog, and nothing here runs locally as a server. Since 2026-07-26 the repo also holds the **TV display source** (`display/display.html`), the **shared contract** (`shared/contract.js`), and three small node/bash scripts (`scripts/`: contract drift-check, display assembler, display publisher). Editing any file requires a manual deployment step (see below).

**How changes get verified — `bash tests/run.sh`, and it MUST be green before any deploy.** Nothing runs locally as a server, so the harnesses in **`tests/`** load the **actual** source and replay acceptance scenarios: the inline `<script>` from `index.html` is extracted and evaluated with `new Function`, and `feeding_report_backend_v2.js` is loaded with the Apps Script globals stubbed (`SpreadsheetApp`, `UrlFetchApp`, `CacheService`, `LockService`, `PropertiesService`, `Utilities`, plus a controllable clock). `run.sh` chains syntax → contract drift → backend (64) → tablet (35). **This used to be a throwaway harness rebuilt per session; it became a committed suite on 2026-08-04** after a day-long outage that a persisted regression test would have caught. Each group's reason-for-existing is in `tests/README.md` — read it before deleting a scenario. Older scenarios still covered: offline-add-survives-reconnect, crash recovery, submit-gating on Telegram failure, delete-stays-deleted, malformed-row normalization (2026-06-02 `CHANGELOG.md`).

⚠️ **A green suite is not a working deploy.** A stubbed Apps Script has no write-visibility semantics, no concurrency and no n8n — on 2026-08-04 a 30/30-green suite still had a silent data-loss bug in the diff. After deploying, exercise the real path and read the real response.

### Sync model — durable outbound mutation queue (read this before touching sync code)

The 2026-06-02 rework replaced the old localStorage-*snapshot* reliability layer with a **persisted outbound mutation queue** (`mutationQueue`, localStorage key `feedingManager.queue.v1`). Every local edit is an `{op, dogId, payload}` where `op` ∈ `add | update | delete | mealType`. The `sync*` functions are thin wrappers that **enqueue** and call `flushQueue()`; the queue (not the call site) owns ordering, retry, and offline persistence. Invariants to preserve:

- `enqueue(op, dogId, payload)` **collapses ops before they reach the queue** (this is what bounds queue growth and merges offline edits — preserve it): a `delete` removes all prior ops for that `dogId` and short-circuits entirely if there was an unsynced `add`; an `update` is `Object.assign`-merged into the latest pending `add`/`update` for the dog (not appended); a `mealType` op replaces any earlier `mealType`.
- `flushQueue()` drains in order, removing an item only after its POST succeeds, and distinguishes a **network failure** (flips `isOnline=false`, keeps the item, retries next cycle) from an **op-level rejection** (`success:false` but server reachable: `isOnline` stays true so no false offline banner; a `delete` rejection is treated as done since the row is already gone; other ops increment `attempts` and are dropped at ≥5 so they can't wedge). `isFlushing` guards re-entry.
- `applyRemoteState()` **merges** the server snapshot with the queue — the server is authoritative *only* for dogs with no pending op (pending adds kept, updates re-applied, deletes suppressed). It must **never** wholesale-replace `dogs`/`pens`; that was the original silent-data-loss bug. After rebuilding membership it **sorts each pen by the merged `position`** (stable; legacy/0 ties keep server-row order), and the pending-update overlay carries `position` so an in-flight reorder isn't clobbered by a poll — see "Within-pen feeding order".
- Connection state: `isOnline` is optimistic and flips false only after `OFFLINE_THRESHOLD` (2) consecutive failures (debounces flaky wifi). All GAS calls go through `gasFetch(url, opts, timeoutMs)` (AbortController, default `FETCH_TIMEOUT_MS` 12s). **The third arg is the fix for the 2026-08-04 outage:** one flat 12s budget was applied to *every* call including `getTodayPlan`, which is legitimately slow (it fans out to the Whiteboard and, at Lunch, the master pen sheet — measured 2.8–33s). The tablet was aborting **itself**, and `"signal is aborted without reason"` is Chrome/Android's `AbortError` message, **not** a network fault — if you ever see it again, suspect this budget before suspecting wifi. `addDogsForToday` passes `PLAN_FETCH_TIMEOUT_MS` (45s) + one retry; every other caller omits the arg and keeps 12s (asserted by `tests/tablet.test.js` S7). The 7s heartbeat (`getSessionVersion`) has an in-flight guard and only marks *reachable* + triggers a flush — it never clears the "unsynced" state by itself.
- `updateConnectionUI()` is the **single owner** of the banner + Submit-button state; **Submit is enabled only when `isOnline && queue empty`.**
- There is no longer any localStorage *snapshot* or `maybeRestoreLocalSnapshot` — the queue is the durable store. Don't reintroduce them, and don't add `if(!isOnline) return` early-returns back into the `sync*` functions.
- **Editing pause:** every mutating action calls `pauseSync()` (8s, `SYNC_PAUSE_DURATION`) so the ~5s poll can't fight an in-progress edit; `pollForUpdates` also skips while `!initialLoadComplete` or offline, and piggybacks a 60s `loadDogList` refresh (`DOG_LIST_REFRESH_INTERVAL`) so newly-added Lookup dogs appear without a reload. Note `isSyncing` and `pendingDogIds` are read in the poll gate but **never set** (vestigial) — the live guards are `isSyncPaused()`/`initialLoadComplete`/`isOnline`, plus `isFlushing`/`heartbeatInFlight`.

The 2026-06-02 `CHANGELOG.md` entry documents the rework and which review findings each piece closes.

### Within-pen feeding order (drag-to-reorder, 2026-06-03)

Staff can drag a dog **up/down within its own pen** (incl. to the top), not just between pens. Within-pen order is the array order of `pens[penId]`, persisted per-dog as the Session `Position` column so it **syncs across tablets, survives reload, and flows into the submit/Telegram order**. Pieces (in `index.html` unless noted):
- `computeDropIndex(penEl, draggedId, finalY)` hit-tests sibling `.pen-dog` card midpoints (**excluding the dragged card**, so the index matches the array *after* removal) for the insertion slot; `finishDrag` passes it to `moveDogToPen`.
- `moveDogToPen(dogId, penId, index)` splices at `index` (append fallback keeps the 2-arg staging callers working), then `reindexPen()` assigns **dense positions** (`(i+1)*1000`) and syncs only the dogs whose position changed (dragged → `{penId, position}`, shifted → `{position}`). **No new queue op** — `position` rides in the existing `add`/`update` payloads.
- `applyRemoteState` sorts each pen by `position` (the invariant above) — this is what stops the ~5s poll from clobbering a reorder. Render always draws `pens[]` array order, so the UI can't show a half-sorted state.
- Backend (`feeding_report_backend_v2.js`): `SESSION_COLS.POSITION` (col 13); `ensureSessionTab` self-heals **only** the `Position` (col M) header on the existing live tab — unlike `ensureTempHeader_` it does **not** validate/repair the other 12 Session headers, so a wiped earlier header stays wiped (see the global deleted-header re-keying note); `getSessionState` returns it (legacy → 0); `addDogToSession`/`updateDogInSession` persist it; `submitReport`'s `getSessionState` *fallback* path orders dogs by `[pen, position]` (the normal POST-body path is already ordered by the frontend).
- A blue insertion line (`.drop-before` / `.pen-dogs.drop-at-end`, inset `box-shadow` so it never reflows the column) shows where the drop lands; cleared in `finishDrag` and both cancel paths.

## Data flow on submit (the happy path)

1. Tablet `confirmSubmit()` → `submitToBackend()` POSTs `{action:'submitReport', dogs:[...], mealType, date}` to GAS.
2. GAS `submitReport(data)` — **trusts `data.dogs` from the POST body when non-empty** (the tablet's in-memory view is authoritative because local edits may not have reached the Session sheet). Falls back to `getSessionState()` only for legacy/empty callers. Writes the Temp tab, builds a prefilled JotForm URL per dog, posts the Telegram summary grouped by pen, and **only `clearSession()` + returns `success:true` after a confirmed Telegram delivery** — on a send failure it returns `{success:false, telegramSent:false}` and keeps Temp+Session intact for retry.
3. Human reviews the Telegram message and replies `/send` (or `/cancel`).
4. n8n reads the Temp tab, POSTs each row to JotForm, clears Temp (and Session on cancel), replies with a count.

`finalName` resolution in `submitReport` is `dog.matchedName || dog.name || dog.inputName || ''` (prefers the tablet's resolved `name` over the raw typed `inputName`); `status` and `supplementTypes` are normalized at the top of the loop so a malformed row can't silently mis-map or throw after the Temp tab is cleared. Free-text names are Markdown-escaped (`escapeTelegramMarkdown`) before the Telegram send. The frontend (`confirmSubmit`) treats a submit as successful only when `result.success && result.telegramSent`, and preserves the queue/board otherwise.

`submitReport` returns `{success, telegramSent, sessionCleared, dogsProcessed}` (the gate above keys off the first two; `sessionCleared` is additive — `false` means Telegram delivered but the post-send session clear failed twice, so the dogs legitimately remain in Session). Inside the loop it maps feeding-status and supplement IDs to the human labels written to Temp/JotForm via the hardcoded `FEEDING_STATUS_MAP` and `suppMap` — **add any new status/supplement to those maps in lockstep** (unknown status → `'All'` + a `console.warn`; unknown supplement → silently dropped). The Temp `Medicine Supplement` column = `Yes` when `prescription || supplements` (either flag), and the Comments column carries only the prescription text, never supplement detail.

## n8n command handler (`/send` `/cancel` `/status`) — config gotchas

The Telegram review commands are handled by the **live n8n workflow `yaBIrDOVbJTEMsH9`** (edit via the **n8n MCP** `n8n_update_partial_workflow`, not by hand; the repo JSON is a mirror — regenerate it from the live workflow after any change). `Telegram Trigger` → `Command Router` (Switch on `message.text`): `/send` reads the **Temp** tab and POSTs each row to JotForm, `/cancel` clears **Temp + Session**, `/status` reports pending counts. - **⚠️ `getTodayPlan`'s failure contract — the 2026-08-04 outage, do not regress it.** A failed upstream read must **NEVER** be returned as a successful empty day. `fetchJson_` returning `null` for *both* "fetch failed" and "genuinely empty" was the root conflation: a ~40% HTTP-404 rate on the whiteboard web app surfaced to staff as *"No Lunch dogs found on the whiteboard for today"* (an `info` toast!), so they hand-built the board during an outage. Rules now in force: `fetchJson_(url, {attempts, deadlineMs, out})` writes `out.ok`/`out.error`, and **a caller that turns a failed read into an empty list is a bug**; `getLunchPlan_`/`getBoardingPlan_` return `success:false` on a failed read *and* on a 200 carrying `success:false` (e.g. a rejected `CHECKINOUT_TOKEN`); `readPenMap_` reports `ok`/`error` so an unreadable pen sheet is an outage too — but **zero `"Lunch Y?"` rows is a legitimate quiet day, NOT a failure** (treating it as one blacked the button out for a whole day with no override). A genuinely empty roster stays `success:true`.
- **Response fields beyond the core shape** (all additive; the tablet ignores what it doesn't know): `stale:true` + `capturedAt` + `upstreamError` when a last-known-good copy is served during an outage — the tablet puts this in the **`confirm()` text**, not a toast, because `confirm()` blocks and a toast may never paint; `rosterSource:'sheet'|'webapp'` + `rosterFallbackReason` so a silent slide back to the flaky web app is visible from outside; `cached:true` on a cache hit, purely diagnostic.
- **Caching** (`CONFIG.PLAN_CACHE_*`): a **fresh** copy (120s) short-circuits the upstream, and a **last-known-good** copy (2700s — *not* the 6h cap, because the tablet merges without removing and a stale roster can put a departed dog into a live feeding round) is served **only** on failure. Keys carry `(v1, today, mealPeriod)` so an LKG can never cross midnight or meals, and an **empty** LKG is refused — serving it would fire the stale warning *and* "no dogs found" together. `?fresh=1` bypasses the cache; the tablet sends it on any repeat press (the staff gesture for "I just ticked Lunch Y?"). All cache calls are best-effort: a cache fault degrades to a live read, never an error.
- **Retry policy is deliberately asymmetric.** No retry against the whiteboard web app (`attempts: 1`): its failures take 16–43s so a retry could never clear the deadline gate, and the producer documents that its `/exec` degrades under concurrent load — retrying would deepen the outage. Retry stays armed only on the fast, healthy check-in/out feed.
- The handler returns `{success, mealPeriod, today, dogs:[{name, penGroup:'top'|'bottom'|null}], skipped, counts}`. The frontend **merges** (skips names already on the board), sets the meal type, and assigns each dog to the **least-occupied eligible pen** (`pickLeastOccupiedPen` — all 10 pens for breakfast/dinner; the B/T side for lunch), so the spread balances even on a non-empty board. ## Conventions and gotchas specific to this codebase

- **Communication with GAS is action-dispatch over a single endpoint.** `doGet` switches on `?action=` (`getDogList`, `getSession`, `getSessionVersion`, `getTodayPlan`, `repairTemp`); `doPost` switches on `data.action` (`addDog`, `updateDog`, `deleteDog`, `setMealType`, `submitReport`, `clearSession`, `getTemp`, `clearTemp`, `getTodayPlan` — plus `getDogList`/`getSession`, which `doPost` also accepts even though GET is the primary path for those two). Every handler returns `{success, ...}` or `{success:false, error}` — never throws to the client. Use `redirect: 'follow'` on fetches (GAS 302-redirects).
- **The Temp tab's row-1 header is load-bearing and self-healing.** `ensureTempHeader_(sheet)` (canonical header in `CONFIG.TEMP_HEADER`) rebuilds row 1 — and re-seats any stray dog rows — whenever it's missing; it's called at the top of `submitReport` and in `clearTempTab`, so a wiped header can't poison the next n8n read. `?action=repairTemp` (doGet) runs it on the live tab on demand (recovery). Don't remove these calls or hard-code the header elsewhere. To POST actions via `curl`, do **not** use `-X POST` — it forces POST onto GAS's 302 redirect hop and 411s; `curl -sL -d '{...}' <exec>` is correct.
- **Session versioning is REAL now (2026-07-26, @29 — was loose before).** `getSession` and `getSessionVersion` both return the **same monotonic version** from the hidden **Meta** tab (`max(Date.now(), stored+1)`, bumped inside every mutation's script lock — including **deletes and clears**, which the old `max(Last_Updated)` scheme could never signal). The tablet poll's `version > lastSyncVersion` gate is now genuinely change-gated (`applyRemoteState` runs only when something changed; the queue merge still protects unsynced edits when it does), and the TV display's adaptive refresh no longer oscillates (pre-@29, `getSession` returned an always-fresh `Date.now()` that could never match `getSessionVersion`, locking the TV in a permanent ~40s fast-mode loop ≈26k full reads/day). **Response contract — preserve it:** `addDog`/`updateDog`/`deleteDog`/`setMealType` responses carry **NO `version` field** (the tablet's guarded `flushQueue` must not advance `lastSyncVersion` past never-applied remote edits — that's what makes offline-window edits from another device reach a reconnecting tablet); `clearSession` **keeps** `version` (the tablet's `syncClearSession` assigns it unguarded — omitting it would poison the gate with `undefined` and kill polling). Counts from both endpoints use the same non-empty-`Dog_ID` predicate (the TV compares count too). **Self-heal:** an out-of-band Session edit that changes the row count (n8n `/cancel`'s whole-tab wipe, a manual row add/delete) is detected as count-drift vs Meta on the next read and bumps the version so every client refetches; an **in-place cell edit** made directly in the Sheets UI is NOT detected until the next mutation.
- **All session mutators run under `LockService`'s script lock (2026-07-26, @29).** `addDog`/`updateDog`/`deleteDog`/`setMealType`/`clearSession` (+ `submitReport`'s Temp rebuild, `clearTempTab`, `repairTemp`) serialize via `withScriptLock_` — closes the cross-device row-shift race where a concurrent add/delete shifted an update onto the wrong dog's row. Details that are load-bearing: **`deleteDog` waits 20s** (longer than the tablet's 12s fetch abort) because the live tablet dequeues ANY `success:false` delete as "already gone" — contention must surface as a client abort (retried), never a droppable rejection; the **Telegram send stays OUTSIDE the lock** (a hung UrlFetchApp must not starve other writes); reads never take the lock (the drift self-heal uses `tryLock(0)` and skips if busy); version bumps after an irreversible write are best-effort (`tryBumpSessionVersion_`) so a Meta hiccup can't fail a landed write into a duplicate-append retry. `submitReport` now also returns `sessionCleared` (additive) and retries a failed post-Telegram clear once.
- **⚠️ `addDog` MUST stay idempotent by `Dog_ID` — never revert it to a bare `appendRow` (2026-08-04, @34).** The tablet's durable queue retries an `add` whenever the POST didn't *visibly* succeed, and a client-side fetch abort is indistinguishable from a real failure even when the server **landed** the write. A blind append writes the dog again on every retry: the live Session tab reached **37 rows for 16 dogs** (one dog ×5). `addDogToSessionCore_` now looks up the `Dog_ID` and *updates* that row instead (safe — it is already inside the script lock), returning `deduped:true` on a replay; a replay refreshes the row so a retry carrying a newer pen/position still wins. **The asymmetry that hid this for so long:** the tablet's `applyRemoteState` rebuilds pens keyed by dog id so duplicates collapse invisibly, while the TV display's `applyData` pushes every row — so **the display is the only surface that shows this class of corruption**, and "only the TV is wrong" almost certainly means the TV is right. Recovery for an already-polluted tab: `?action=dedupeSession` (keeps the last row per `Dog_ID`; safe no-op when clean). Regression tests: `tests/backend.test.js` group **M**.
- **Defensive JSON parse is mandatory.** Session cells holding arrays (`Possible_Matches`, `Supplement_Types`) go through `safeJsonParse(value, fallback)` so one corrupt cell can't break `getSessionState()` for every device. Keep that pattern for any new JSON-bearing column.
- **Dog name matching is two-tier and lives in the frontend.** `matchDogName` (exact first-name + surname-initial prefix) for the primary match; `fuzzyMatchDogName` (scored, top 15) for the "possible matches" picker. The Lookup tab is the primary name source, but `loadDogList` keeps the inline `JOTFORM_DOG_NAMES` hardcoded fallback (and does **not** overwrite `dogNameList`) unless Lookup returns ≥ `MIN_DOG_COUNT` (10) dogs — so a near-empty/failed Lookup does **not** break matching; it logs a warning and matches against the fallback list.
- **Drag-and-drop is fragile and tablet-tuned.** Touch + mouse handlers, a `LONG_PRESS_DURATION` long-press timer, the `is-dragging` body class, and Android `touch-action` quirks are deliberately hand-balanced. The offline banner is `position:fixed` specifically so it never reflows the drag layout. The **same gesture also reorders within a pen** (drop between cards → `computeDropIndex`; see "Within-pen feeding order"), and cross-pen drops now land at the drop position rather than always appending. If you change any drag/drop CSS or touch handler, re-run the on-tablet drag smoke test.
- **The `sync*` functions now just enqueue** (`syncAddDog/UpdateDog/DeleteDog/MealType`) and trigger a flush (`syncMealType` additionally calls `pauseSync()` first; the other three are pure enqueue+flush); the trailing `quiet` arg is accepted for call-site compatibility but ignored. Mutations are durable and replayed on reconnect — see **Sync model → `enqueue()`** for the op-collapse rules.
- **Pen IDs are fixed strings:** `top-1`…`top-5`, `bottom-1`…`bottom-5`. Meal types: `Morning Meal`, `Lunch` (default), `Evening Meal`. The **canonical copy** of the pen order (and the status value set, exec URL, fetch timeout) is **`shared/contract.js`** (since 2026-07-26); the display consumes it directly at publish time, while the tablet + backend keep inline copies in **four** places — frontend `PEN_ORDER` (drives `pickLeastOccupiedPen`) and a second `penOrder` in the submit-preview/Telegram render; backend `penOrder` in `sendTelegramSummary` and `penRank` in `submitReport`'s fallback path (unknown pens default to rank 99). **`node scripts/check_contract.js` asserts every copy matches the contract** (publish_display.sh runs it automatically) — run it after touching any of them; change the contract FIRST, then the copies.

## Telegram URL encoding (project-wide rule)

When building any URL that a mobile Telegram user will tap, **emit zero `%XX` sequences** — iOS Telegram double-encodes them and breaks the target app. This backend's `mobileEncode()` already converts `%20`→`+` and unescapes `@ : /`. See the user-level memory note on the Telegram-iOS issue #138 workaround before adding any new outbound link.

## Deployment checklist when you change a file

- **`index.html`** → `git push origin main`; GitHub Pages serves it (CDN cache ~1–2 min; cache-bust with `?cb=<ts>` when verifying). No other step.
- **`feeding_report_backend_v2.js`** → deploy with **clasp** (already authenticated via `~/.clasprc.json`): in a throwaway temp dir run `clasp clone-script <scriptId>`, `cp` this file over the cloned `Code.js`, `clasp push -f`, then `clasp redeploy <deploymentId> -d "…"` to push a new version onto the **existing web-app deployment** (same `/exec` URL). Do **not** `clasp deploy` fresh — that mints a new URL the tablet doesn't use. The script ID + deployment ID are in Claude's private project memory (`feeding-manager-deploy`) and in Apps Script → Project Settings. **Gotcha (broke prod once, 2026-06-03):** `clasp push` pushes *every* file in the clone dir, and prints "Script is already up to date" (skipping the push) when `Code.js`/`appsscript.json` are unchanged. So (a) never leave a stray `.js` in that dir — a temp diff copy = a second `const CONFIG`/functions = the whole web app 500s with `SyntaxError: Identifier 'CONFIG' has already been declared`; do drift-diffs in a *different* directory — and (b) deleting a remote-only file locally won't remove it; force a real content change (marker → push → clean push). **Always `curl ".../exec?action=getSessionVersion"` after every redeploy** to confirm it still compiles. **Network ops (git push, clasp, curl) require the Bash tool's sandbox disabled.**
- **Feeding Display (`display/display.html` + `shared/contract.js`)** → **`bash scripts/publish_display.sh "commit message"`** (Git Bash; network ops need the sandbox disabled). The script runs `node scripts/check_contract.js` (aborts on any tablet/backend/contract drift), injects `shared/contract.js` at the `// @@CONTRACT@@` marker (`scripts/assemble_display.js`, LF-normalised), clones **`Fairytails123/frmdisplay`**, sets the git identity, overwrites `index.html`, commits + pushes. `--dry-run` assembles + checks without pushing. Verify at https://fairytails123.github.io/frmdisplay/?cb=<ts> (~1–2 min CDN); **the TV needs a browser refresh to pick it up**. Never deploy the display any other way, and never edit the retired OneDrive copy.
- **`n8n_workflow_v2_corrected.json`** → edit the **live workflow `yaBIrDOVbJTEMsH9`** in n8n via the **n8n MCP** (`n8n_update_partial_workflow`, surgical diff ops; run with `validateOnly:true` first), then regenerate this mirror from the live workflow (`n8n_get_workflow`).
