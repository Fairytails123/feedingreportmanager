## What this is

A **Feeding Report Manager** for a dog daycare/boarding operation. Staff use a tablet web app during a feeding session to log which dogs ate how much, plus medicine/supplements, by dragging dog cards into physical "pen" slots. On submit, the system emails-prefills a JotForm per dog and posts a review summary to a Telegram group; a human replies `/send` in Telegram and an n8n workflow pushes the staged data into JotForm.

There is **no build, test, or lint tooling** in the traditional sense — the sources are hand-edited files plus a changelog, and nothing here runs locally as a server. Since 2026-07-26 the repo also holds the **TV display source** (`display/display.html`), the **shared contract** (`shared/contract.js`), and three small node/bash scripts (`scripts/`: contract drift-check, display assembler, display publisher). Since 2026-08-05 it also holds **`design_handoff_feeding_board/`** — the Claude Design handoff that the current UI implements. **It is the design source of truth for colours, sizes, spacing and copy**: `README.md` is the spec, `INTEGRATION.md` lists the production behaviours that must survive a UI change, and `designs/*.dc.html` carry the authoritative inline values. ⚠️ **Read `design_handoff_feeding_board/AS-BUILT.md` before acting on any of it** — the shipped UI deliberately differs from the spec in a handful of places (the portion control is a `<select>`, not the spec's segmented control; `@media` not `@container`; `rgba()` not `color-mix()`; drag listeners on `document`), each with the measurement or the owner decision behind it. A session that "restores the spec" without reading that file will undo work. Editing any file requires a manual deployment step (see below).

**How changes get verified — `bash tests/run.sh`, and it MUST be green before any deploy.** Nothing runs locally as a server, so the harnesses in **`tests/`** load the **actual** source and replay acceptance scenarios: the inline `<script>` from `index.html` is extracted and evaluated with `new Function`, and `feeding_report_backend_v2.js` is loaded with the Apps Script globals stubbed (`SpreadsheetApp`, `UrlFetchApp`, `CacheService`, `LockService`, `PropertiesService`, `Utilities`, plus a controllable clock). `run.sh` chains syntax → contract drift → backend (80) → tablet (82) → display (9), plus 27 LIVE n8n assertions under `LIVE=1`. **This used to be a throwaway harness rebuilt per session; it became a committed suite on 2026-08-04** after a day-long outage that a persisted regression test would have caught. Each group's reason-for-existing is in `tests/README.md` — read it before deleting a scenario. Older scenarios still covered: offline-add-survives-reconnect, crash recovery, submit-gating on Telegram failure, delete-stays-deleted, malformed-row normalization (2026-06-02 `CHANGELOG.md`).

⚠️ **A green suite is not a working deploy.** A stubbed Apps Script has no write-visibility semantics, no concurrency and no n8n — on 2026-08-04 a 30/30-green suite still had a silent data-loss bug in the diff. After deploying, exercise the real path and read the real response.

## ⚠️ THE LIVE SESSION IS IN n8n, NOT THE SHEET (since @36, 2026-08-05)

**Every session read and write — `getSessionVersion`, `getSession`, `addDog`, `updateDog`,
`deleteDog`, `setMealType`, `clearSession` — goes to the n8n webhook
`https://auto.thefairytails.co.uk/webhook/feeding-session`** (workflow `hdGUbrd0PffVnwDS`, Data
Tables `feeding_session` `nnbHmglWVbneFigg` + `feeding_meta` `5TGDqjRVlrczGUgm`). The **Session
tab is now a best-effort MIRROR** that n8n writes; do not treat it as authoritative and do not
point a new reader at it.

**Why** — measured live on 2026-08-05, same test both sides: Apps Script `/exec` median **4.5–8.7s
with a 55.6s peak**, ~40% of calls past the tablet's 12s budget, plus Google 404s; n8n **0.70s
mean, 1.83s worst, zero failures**. The decisive experiment: a bare `/exec` ping doing **no
spreadsheet work at all** was just as slow (55.6s worst), so the bottleneck was Apps Script's
**dispatch** layer — not the data, not the code. Caching `getSessionVersion` (the original plan)
would have bought nothing. Apps Script allows ~30 simultaneous executions **per Google account**,
shared with Staff Board, Training Planner, Boarding API, Grooming and Order list.

**Apps Script KEEPS** `submitReport`, `getTodayPlan` and `getDogList` — a handful of calls a day,
each with its own generous budget. `submitReport` additionally clears the n8n board
(`clearLiveBoard_`, reported as `liveBoardCleared`) because the TV reads n8n.

**Invariants that must survive any future change here** (each is a bug that already happened):
- **ONE version source.** `getSession` and `getSessionVersion` both serve the same stored value
  from `feeding_meta`. Two sources can never compare equal and pin clients in permanent fast mode.
- **Mutation responses carry NO `version`; `clearSession` DOES.** The tablet assigns the latter
  unguarded, so omitting it poisons the poll gate with `undefined`.
- **Partial updates emit only changed columns** (`autoMapInputData`), so two tablets editing
  different fields of one dog don't clobber each other.
- **The mirror is ONE atomic fixed-height range write** (`A2:M201`). It was clear-then-append and
  that CORRUPTED the sheet — concurrent executions interleaved and a 2-dog board mirrored as 6
  rows with duplicates. Never reintroduce a separate clear step.
- ⚠️ **The Data Table node advertises a `table/clear` operation its runtime router does NOT
  implement.** `clearSession` returned an empty body and silently left the board populated, and
  `n8n_validate_workflow` passed it clean. Use `row/deleteRows` with an always-true filter.

### Sync model — durable outbound mutation queue (read this before touching sync code)

The 2026-06-02 rework replaced the old localStorage-*snapshot* reliability layer with a **persisted outbound mutation queue** (`mutationQueue`, localStorage key `feedingManager.queue.v1`). Every local edit is an `{op, dogId, payload}` where `op` ∈ `add | update | delete | mealType`. The `sync*` functions are thin wrappers that **enqueue** and call `flushQueue()`; the queue (not the call site) owns ordering, retry, and offline persistence. Invariants to preserve:

- `enqueue(op, dogId, payload)` **collapses ops before they reach the queue** (this is what bounds queue growth and merges offline edits — preserve it): a `delete` removes all prior ops for that `dogId` and short-circuits entirely if there was an unsynced `add`; an `update` is `Object.assign`-merged into the latest pending `add`/`update` for the dog (not appended); a `mealType` op replaces any earlier `mealType`.
- ⚠️ **…but NEVER into an item that is already on the wire (`it.inFlight`) — silent data loss, found live 2026-08-05 (@37).** `flushQueue` serialises an item's payload the moment it POSTs it and removes the item on success, so merging into that payload writes fields into an object that has already gone and is about to be discarded. Live repro on the redesigned tile (portion + medicine + supplements are now one panel, so staff fire three edits inside one ~700ms round-trip): tapping ½ → Medicine → typing "Metacam" landed **only the ½**, no error anywhere — and a direct `updateDog` curl with the same fields wrote them fine, which is what proved the n8n handler innocent. Two siblings from the same read: a `delete` for a dog whose `add` was in flight was collapsed to "never synced" and **orphaned the row server-side**; and `flushQueue` removed the finished item with `shift()` ("whatever is at index 0 *now*"), so an `enqueue` that rebuilt the array mid-flight **discarded a different dog's edit, unsent**. Now: `inFlight` is set before the POST, `enqueue` refuses to merge into or filter away such an item, `loadQueue` strips the flag (a reload means nothing is on the wire), and items are removed **by identity**, never by position. Regression tests: `tests/tablet.test.js` group **S22** (negative-control tested — 5 of its 13 checks fail against the pre-fix build).
- `flushQueue()` drains in order, removing an item only after its POST succeeds, and distinguishes a **network failure** (flips `isOnline=false`, keeps the item, retries next cycle) from an **op-level rejection** (`success:false` but server reachable: `isOnline` stays true so no false offline banner; a `delete` rejection is treated as done since the row is already gone; other ops increment `attempts` and are dropped at ≥5 so they can't wedge). `isFlushing` guards re-entry.
- `applyRemoteState()` **merges** the server snapshot with the queue — the server is authoritative *only* for dogs with no pending op (pending adds kept, updates re-applied, deletes suppressed). It must **never** wholesale-replace `dogs`/`pens`; that was the original silent-data-loss bug. After rebuilding membership it **sorts each pen by the merged `position`** (stable; legacy/0 ties keep server-row order), and the pending-update overlay carries `position` so an in-flight reorder isn't clobbered by a poll — see "Within-pen feeding order".
- Connection state: `isOnline` is optimistic and flips false only after `OFFLINE_THRESHOLD` (2) consecutive failures (debounces flaky wifi). All GAS calls go through `gasFetch(url, opts, timeoutMs)` (AbortController, default `FETCH_TIMEOUT_MS` 12s). **The third arg is the fix for the 2026-08-04 outage:** one flat 12s budget was applied to *every* call including `getTodayPlan`, which is legitimately slow (it fans out to the Whiteboard and, at Lunch, the master pen sheet — measured 2.8–33s). The tablet was aborting **itself**, and `"signal is aborted without reason"` is Chrome/Android's `AbortError` message, **not** a network fault — if you ever see it again, suspect this budget before suspecting wifi. `addDogsForToday` passes `PLAN_FETCH_TIMEOUT_MS` (45s) + one retry; every other caller omits the arg and keeps 12s (asserted by `tests/tablet.test.js` S7). **The separate 7s heartbeat is GONE (2026-08-05, @35)** — `pollForUpdates` absorbed it; see the next bullet.
- `updateConnectionUI()` is the **single owner** of the banner + Submit-button state; **Submit is enabled only when `isOnline && queue empty`.**
- There is no longer any localStorage *snapshot* or `maybeRestoreLocalSnapshot` — the queue is the durable store. Don't reintroduce them, and don't add `if(!isOnline) return` early-returns back into the `sync*` functions.
- **One version-first poll (@35, 2026-08-05) — do NOT re-add the old entry gate.** `pollForUpdates` runs every `SYNC_INTERVAL` (5s, unchanged) and costs **one cheap `getSessionVersion`**; the full `getSession` only runs when the version actually moved. It replaced the old 5s-full-read + independent 7s heartbeat. Three properties are load-bearing, each asserted by a test:
  - **It runs while EDITING and while OFFLINE** (`tablet.test.js` S13/S14). The old poll bailed out on `isSyncPaused()` and `!isOnline` — *that* is why a separate heartbeat had to exist, to keep proving reachability and draining the queue mid-edit and to notice the link returning. Gating this loop on `isOnline` again makes offline unrecoverable except via the manual Retry button.
  - **The edit pause protects the BOARD, not the connection.** `pauseSync()` (8s, `SYNC_PAUSE_DURATION`) still gates `applyRemoteState` (plus `pendingDogIds`), so a poll can't fight an in-progress edit — but the version probe and `flushQueue` are *not* gated. When skipped, `lastSyncVersion` is deliberately left alone so the change is re-detected next tick.
  - **`isSyncing` is now a REAL in-flight guard** (it was vestigial — read in the gate, never assigned), taking over `heartbeatInFlight`'s anti-stacking job (S16). `pendingDogIds` is still vestigial.
  `loadDogList` piggybacks on the poll at `DOG_LIST_REFRESH_INTERVAL` (**600s** since @35 — Lookup rarely changes) and never while paused; `startForegroundSync()` polls immediately on `visibilitychange` and tops the list up if older than `DOG_LIST_FOCUS_MAX_AGE` (60s), so a picked-up tablet is fresher than the old 60s loop gave.

### Within-pen feeding order (drag-to-reorder, 2026-06-03)

Staff can drag a dog **up/down within its own pen** (incl. to the top), not just between pens. Within-pen order is the array order of `pens[penId]`, persisted per-dog as the Session `Position` column so it **syncs across tablets, survives reload, and flows into the submit/Telegram order**. Pieces (in `index.html` unless noted):
- `computeDropIndex(penEl, draggedId, finalY)` hit-tests sibling `.pen-dog` card midpoints (**excluding the dragged card**, so the index matches the array *after* removal) for the insertion slot; `FRMDrag` passes it to `moveDogToPen` on release. (It used to be passed by `finishDrag`, which the @37 engine rewrite removed — the module-level `draggedDogId`/`draggedFromPen` that `showDropIndicator` reads are still set, now by `FRMDrag` at lift and cleared at release.)
- `moveDogToPen(dogId, penId, index)` splices at `index` (append fallback keeps the 2-arg staging callers working), then `reindexPen()` assigns **dense positions** (`(i+1)*1000`) and syncs only the dogs whose position changed (dragged → `{penId, position}`, shifted → `{position}`). **No new queue op** — `position` rides in the existing `add`/`update` payloads.
- `applyRemoteState` sorts each pen by `position` (the invariant above) — this is what stops the ~5s poll from clobbering a reorder. Render always draws `pens[]` array order, so the UI can't show a half-sorted state.
- Backend (`feeding_report_backend_v2.js`): `SESSION_COLS.POSITION` (col 13); `ensureSessionTab` self-heals **only** the `Position` (col M) header on the existing live tab — unlike `ensureTempHeader_` it does **not** validate/repair the other 12 Session headers, so a wiped earlier header stays wiped (see the global deleted-header re-keying note); `getSessionState` returns it (legacy → 0); `addDogToSession`/`updateDogInSession` persist it; `submitReport`'s `getSessionState` *fallback* path orders dogs by `[pen, position]` (the normal POST-body path is already ordered by the frontend).
- A terracotta insertion line (`.drop-before` / `.pen-dogs.drop-at-end`, inset `box-shadow` so it never reflows the column — a border or margin would shift the very card midpoints `computeDropIndex` reads mid-drag) shows where the drop lands; cleared by `FRMDrag` on release and on every cancel path.

## Data flow on submit (the happy path)

1. Tablet `confirmSubmit()` → `submitToBackend()` POSTs `{action:'submitReport', dogs:[...], mealType, date}` to GAS.
2. GAS `submitReport(data)` — **trusts `data.dogs` from the POST body when non-empty** (the tablet's in-memory view is authoritative because local edits may not have reached the Session sheet). Falls back to `getSessionState()` only for legacy/empty callers. Writes the Temp tab, builds a prefilled JotForm URL per dog, posts the Telegram summary grouped by pen, and **only `clearSession()` + returns `success:true` after a confirmed Telegram delivery** — on a send failure it returns `{success:false, telegramSent:false}` and keeps Temp+Session intact for retry.
3. Human reviews the Telegram message and replies `/send` (or `/cancel`).
4. n8n reads the Temp tab, POSTs each row to JotForm, clears Temp (and Session on cancel), replies with a count.

`finalName` resolution in `submitReport` is `dog.matchedName || dog.name || dog.inputName || ''` (prefers the tablet's resolved `name` over the raw typed `inputName`); `status` and `supplementTypes` are normalized at the top of the loop so a malformed row can't silently mis-map or throw after the Temp tab is cleared. Free-text names are Markdown-escaped (`escapeTelegramMarkdown`) before the Telegram send. The frontend (`confirmSubmit`) treats a submit as successful only when `result.success && result.telegramSent`, and preserves the queue/board otherwise.

`submitReport` returns `{success, telegramSent, sessionCleared, dogsProcessed}` (the gate above keys off the first two; `sessionCleared` is additive — `false` means Telegram delivered but the post-send session clear failed twice, so the dogs legitimately remain in Session). Inside the loop it maps feeding-status and supplement IDs to the human labels written to Temp/JotForm via the hardcoded `FEEDING_STATUS_MAP` and `suppMap` — **add any new status/supplement to those maps in lockstep** (unknown status → `'All'` + a `console.warn`; unknown supplement → silently dropped). The Temp `Medicine Supplement` column = `Yes` when `prescription || supplements` (either flag), and the Comments column carries only the prescription text, never supplement detail.

## n8n command handler (`/send` `/cancel` `/status`) — config gotchas

The Telegram review commands are handled by the **live n8n workflow `yaBIrDOVbJTEMsH9`** (edit via the **n8n MCP** `n8n_update_partial_workflow`, not by hand; the repo JSON is a mirror — regenerate it from the live workflow after any change). `Telegram Trigger` → `Command Router` (Switch on `message.text`): `/send` reads the **Temp** tab and POSTs each row to JotForm, `/cancel` clears **Temp + Session**, `/status` reports pending counts. These were silently broken from launch until 2026-06-02 (every real command errored at the first Google Sheets node while non-command chatter "succeeded" by falling through to no branch). Preserve these invariants — each is a fix for a bug that shipped to production:

- **Google Sheets nodes select the tab by gid, not name.** With the Sheet resource-locator in `mode:"list"`, `value` MUST be the numeric **gid** (`cachedResultName` is just a display label). Putting the tab *name* in `value` throws `Sheet with ID Temp not found`. Gids: **Temp `1965265218`, Session `1038940935`** (Lookup `0`, retired B/T pen `1567330092`). ## Conventions and gotchas specific to this codebase

- **Communication with GAS is action-dispatch over a single endpoint.** `doGet` switches on `?action=` (`getDogList`, `getSession`, `getSessionVersion`, `getTodayPlan`, `repairTemp`); `doPost` switches on `data.action` (`addDog`, `updateDog`, `deleteDog`, `setMealType`, `submitReport`, `clearSession`, `getTemp`, `clearTemp`, `getTodayPlan` — plus `getDogList`/`getSession`, which `doPost` also accepts even though GET is the primary path for those two). Every handler returns `{success, ...}` or `{success:false, error}` — never throws to the client. Use `redirect: 'follow'` on fetches (GAS 302-redirects).
- **The Temp tab's row-1 header is load-bearing and self-healing.** `ensureTempHeader_(sheet)` (canonical header in `CONFIG.TEMP_HEADER`) rebuilds row 1 — and re-seats any stray dog rows — whenever it's missing; it's called at the top of `submitReport` and in `clearTempTab`, so a wiped header can't poison the next n8n read. `?action=repairTemp` (doGet) runs it on the live tab on demand (recovery). Don't remove these calls or hard-code the header elsewhere. To POST actions via `curl`, do **not** use `-X POST` — it forces POST onto GAS's 302 redirect hop and 411s; `curl -sL -d '{...}' <exec>` is correct.
- **Session versioning is REAL now (2026-07-26, @29 — was loose before).** `getSession` and `getSessionVersion` both return the **same monotonic version** from the hidden **Meta** tab (`max(Date.now(), stored+1)`, bumped inside every mutation's script lock — including **deletes and clears**, which the old `max(Last_Updated)` scheme could never signal). The tablet poll's `version > lastSyncVersion` gate is now genuinely change-gated (`applyRemoteState` runs only when something changed; the queue merge still protects unsynced edits when it does), and the TV display's adaptive refresh no longer oscillates (pre-@29, `getSession` returned an always-fresh `Date.now()` that could never match `getSessionVersion`, locking the TV in a permanent ~40s fast-mode loop ≈26k full reads/day). **Response contract — preserve it:** `addDog`/`updateDog`/`deleteDog`/`setMealType` responses carry **NO `version` field** (the tablet's guarded `flushQueue` must not advance `lastSyncVersion` past never-applied remote edits — that's what makes offline-window edits from another device reach a reconnecting tablet); `clearSession` **keeps** `version` (the tablet's `syncClearSession` assigns it unguarded — omitting it would poison the gate with `undefined` and kill polling). Counts from both endpoints use the same non-empty-`Dog_ID` predicate (the TV compares count too). **Self-heal:** an out-of-band Session edit that changes the row count (n8n `/cancel`'s whole-tab wipe, a manual row add/delete) is detected as count-drift vs Meta on the next read and bumps the version so every client refetches; an **in-place cell edit** made directly in the Sheets UI is NOT detected until the next mutation.
- **All session mutators run under `LockService`'s script lock (2026-07-26, @29).** `addDog`/`updateDog`/`deleteDog`/`setMealType`/`clearSession` (+ `submitReport`'s Temp rebuild, `clearTempTab`, `repairTemp`) serialize via `withScriptLock_` — closes the cross-device row-shift race where a concurrent add/delete shifted an update onto the wrong dog's row. Details that are load-bearing: **`deleteDog` waits 20s** (longer than the tablet's 12s fetch abort) because the live tablet dequeues ANY `success:false` delete as "already gone" — contention must surface as a client abort (retried), never a droppable rejection; the **Telegram send stays OUTSIDE the lock** (a hung UrlFetchApp must not starve other writes); reads never take the lock (the drift self-heal uses `tryLock(0)` and skips if busy); version bumps after an irreversible write are best-effort (`tryBumpSessionVersion_`) so a Meta hiccup can't fail a landed write into a duplicate-append retry. `submitReport` now also returns `sessionCleared` (additive) and retries a failed post-Telegram clear once.
- **⚠️ `addDog` MUST stay idempotent by `Dog_ID` — never revert it to a bare `appendRow` (2026-08-04, @34).** The tablet's durable queue retries an `add` whenever the POST didn't *visibly* succeed, and a client-side fetch abort is indistinguishable from a real failure even when the server **landed** the write. A blind append writes the dog again on every retry: the live Session tab reached **37 rows for 16 dogs** (one dog ×5). `addDogToSessionCore_` now looks up the `Dog_ID` and *updates* that row instead (safe — it is already inside the script lock), returning `deduped:true` on a replay; a replay refreshes the row so a retry carrying a newer pen/position still wins. **The asymmetry that hid this for so long:** the tablet's `applyRemoteState` rebuilds pens keyed by dog id so duplicates collapse invisibly, while the TV display's `applyData` pushes every row — so **the display is the only surface that shows this class of corruption**, and "only the TV is wrong" almost certainly means the TV is right. Recovery for an already-polluted tab: `?action=dedupeSession` (keeps the last row per `Dog_ID`; safe no-op when clean). Regression tests: `tests/backend.test.js` group **M**.
- **Defensive JSON parse is mandatory.** Session cells holding arrays (`Possible_Matches`, `Supplement_Types`) go through `safeJsonParse(value, fallback)` so one corrupt cell can't break `getSessionState()` for every device. Keep that pattern for any new JSON-bearing column.
- **Dog name matching is two-tier and lives in the frontend.** `matchDogName` (exact first-name + surname-initial prefix) for the primary match; `fuzzyMatchDogName` (scored, top 15) for the "possible matches" picker. The Lookup tab is the primary name source, but `loadDogList` keeps the inline `JOTFORM_DOG_NAMES` hardcoded fallback (and does **not** overwrite `dogNameList`) unless Lookup returns ≥ `MIN_DOG_COUNT` (10) dogs — so a near-empty/failed Lookup does **not** break matching; it logs a warning and matches against the fallback list.
- **Drag-and-drop is `FRMDrag`, an IIFE inside the inline script (rewritten 2026-08-05, @37).** Long-press (300ms) **anywhere on a tile** picks a dog up; >10px of movement first means it was a scroll and cancels the press. It reuses — and must keep calling — `computeDropIndex`, `moveDogToPen`, `deleteDog`, `showDropZones`, `hideDropZones`, `showDropIndicator`, `clearDropIndicator`, `triggerHaptic`, `showToast`, `getDogDisplayName`. Five things are load-bearing; each is why the old engine died on Android:
  1. **The non-passive `touchmove` is registered ONCE AT INIT**, not when a drag starts. Chrome decides whether a gesture is a scroll on its first moves — a listener attached 300ms later cannot cancel one.
  2. **`setPointerCapture` is taken at LIFT, never on `pointerdown`.** Capturing on pointerdown retargets `pointerup`, so the browser resolves the click against the tile instead of the button inside it, and every tap on the portion segments and the chevron dies.
  3. **There is NO `body.is-dragging { overflow:hidden }`.** That lock is what made the page jump under the finger. Scrolling is stopped by cancelling `touchmove`, and the board **auto-scrolls at the edges** instead (proportional, driven by ONE persistent rAF — a finger parked in the edge zone emits no `pointermove`, so a move-driven loop would stall exactly when the user is asking it to keep going).
  4. **`pointermove`/`up`/`cancel` live on `document`, not the tile** (deviation from the handoff engine, on purpose): an element listener dies if the node is replaced mid-gesture, which is precisely when a drag must not be dropped. `pollForUpdates` additionally refuses to `applyRemoteState` while `isDragActive()`.
  5. **The drop is hit-tested FRESH at release**, not read off the last painted highlight (which can be a frame behind, or never have run).
  6. **(2026-08-10) `body` carries `overscroll-behavior-x: none; overscroll-behavior-y: auto` — the y-axis MUST stay `auto`.** With `none` (or `contain`) on the viewport, Android Chrome refuses to chain the vertical part of a touch gesture that starts inside `.fb-pens` (a horizontal scroll container) up to the page scroller, so a populated board could not be scrolled up/down at all on a phone. `x` stays `none` (suppresses the horizontal history-swipe); pull-to-refresh still can't interrupt a drag because the engine preventDefaults `touchmove` while dragging. Regression test: `node tests/android-scroll.smoke.mjs` (standalone, real CDP touch events; negative-control verified).
  Tiles keep `touch-action: pan-y` at rest (`none` only while dragging) so the board still scrolls when a finger lands on one, and `contextmenu` is suppressed on tiles so Android's long-press menu can't cover the drag. `data-nodrag` opts the portion control, the expanded panel and unmatched staging cards out. The offline banner stays `position:fixed` so it never reflows the drag layout. The **same gesture reorders within a pen** (drop between cards → `computeDropIndex`), and cross-pen drops land at the drop position. There is also a **keyboard path** (Space to lift, arrows to move, Enter to drop, Escape to cancel, announced via `#dragLiveRegion`) which deliberately ignores keys inside inputs. **Mouse testing cannot catch this class of bug — re-run the on-tablet drag smoke test after any change** (see the `frontend-gotchas` skill).
- **The UI is the Organic design system (2026-08-05, @37)** — warm cream ground, terracotta + sage, Caprasimo over Figtree, no emoji, Lucide-style inline SVG at `stroke-width:2.75`. Source of truth: `design_handoff_feeding_board/`. Two deliberate deviations, both for device robustness, both commented in the file: `color-mix()` is written as the equivalent `rgba()`, and the layout uses viewport `@media` rather than `@container` (the board **is** the page, so the pixels are identical, and an unsupported `@container` block would silently drop the whole layout on an older tablet browser). The dog tile is two rows — name + chevron, then the portion control with the medicine/supplement badges beside it — and taps open a panel for medicine/supplements/remove. **The portion control is a `<select>`, NOT the handoff's 5-way segmented control (owner decision, 2026-08-05).** Five side-by-side targets set a wide floor on the tile, the tile sets the pen width, and on a phone in portrait that meant **one pen on screen at a time**; the dropdown costs one extra tap and buys a ~150px pen, so 2–3 pens are visible and a dog can be carried between them without an off-screen drag. The portion stays colour-coded on the closed control *and* on the tile's left edge, which is what the segmented control was really buying. Three sizing rules are load-bearing and each fixed a real clip: `.fb-pen`/`.pen-dog` carry **`min-width: 0`** (a flex item's automatic minimum size is its *min-content* size, so one wide descendant — the expanded panel's "Take off the board" — silently overrode the flex-basis and widened every pen); the badges live on the portion row, not the name row (two badges plus the chevron left the name ~34px, i.e. `"De…"`); and `.portion-wrap` has a **`min-width: 88px`** with the row set to `flex-wrap`, so the badges drop to their own line rather than squeezing `"None"` into its own chevron. **`renderPen` rebuilds a pen's innerHTML, so it restores the open tile (`expandedDogId`) and the caret in the medicine input** (`captureFocus`/`restoreFocus`); don't remove that. Deleting from a *collapsed* tile is gone by design: delete is the bin or the button inside the expanded panel.
- **The `sync*` functions now just enqueue** (`syncAddDog/UpdateDog/DeleteDog/MealType`) and trigger a flush (`syncMealType` additionally calls `pauseSync()` first; the other three are pure enqueue+flush); the trailing `quiet` arg is accepted for call-site compatibility but ignored. Mutations are durable and replayed on reconnect — see **Sync model → `enqueue()`** for the op-collapse rules.
- **Pen IDs are fixed strings:** `top-1`…`top-5`, `bottom-1`…`bottom-5`. Meal types: `Morning Meal`, `Lunch` (default), `Evening Meal`. The **canonical copy** of the pen order (and the status value set, exec URL, fetch timeout) is **`shared/contract.js`** (since 2026-07-26); the display consumes it directly at publish time, while the tablet + backend keep inline copies in **four** places — frontend `PEN_ORDER` (drives `pickLeastOccupiedPen`) and a second `penOrder` in the submit-preview/Telegram render; backend `penOrder` in `sendTelegramSummary` and `penRank` in `submitReport`'s fallback path (unknown pens default to rank 99). **`node scripts/check_contract.js` asserts every copy matches the contract** (publish_display.sh runs it automatically) — run it after touching any of them; change the contract FIRST, then the copies.

## Telegram URL encoding (project-wide rule)

When building any URL that a mobile Telegram user will tap, **emit zero `%XX` sequences** — iOS Telegram double-encodes them and breaks the target app. This backend's `mobileEncode()` already converts `%20`→`+` and unescapes `@ : /`. See the user-level memory note on the Telegram-iOS issue #138 workaround before adding any new outbound link.

## Deployment checklist when you change a file

- **`index.html`** → `git push origin main`; GitHub Pages serves it (CDN cache ~1–2 min; cache-bust with `?cb=<ts>` when verifying). No other step.
- **`feeding_report_backend_v2.js`** → deploy with **clasp** (already authenticated via `~/.clasprc.json`): in a throwaway temp dir run `clasp clone-script <scriptId>`, `cp` this file over the cloned `Code.js`, `clasp push -f`, then `clasp redeploy <deploymentId> -d "…"` to push a new version onto the **existing web-app deployment** (same `/exec` URL). Do **not** `clasp deploy` fresh — that mints a new URL the tablet doesn't use. The script ID + deployment ID are in Claude's private project memory (`feeding-manager-deploy`) and in Apps Script → Project Settings. **Gotcha (broke prod once, 2026-06-03):** `clasp push` pushes *every* file in the clone dir, and prints "Script is already up to date" (skipping the push) when `Code.js`/`appsscript.json` are unchanged. So (a) never leave a stray `.js` in that dir — a temp diff copy = a second `const CONFIG`/functions = the whole web app 500s with `SyntaxError: Identifier 'CONFIG' has already been declared`; do drift-diffs in a *different* directory — and (b) deleting a remote-only file locally won't remove it; force a real content change (marker → push → clean push). **Always `curl ".../exec?action=getSessionVersion"` after every redeploy** to confirm it still compiles. **Network ops (git push, clasp, curl) require the Bash tool's sandbox disabled.**
- **Feeding Display (`display/display.html` + `shared/contract.js`)** → **`bash scripts/publish_display.sh "commit message"`** (Git Bash; network ops need the sandbox disabled). The script runs `node scripts/check_contract.js` (aborts on any tablet/backend/contract drift), injects `shared/contract.js` at the `// @@CONTRACT@@` marker (`scripts/assemble_display.js`, LF-normalised), clones **`Fairytails123/frmdisplay`**, sets the git identity, overwrites `index.html`, commits + pushes. `--dry-run` assembles + checks without pushing. Verify at https://fairytails123.github.io/frmdisplay/?cb=<ts> (~1–2 min CDN); **the TV needs a browser refresh to pick it up**. Never deploy the display any other way, and never edit the retired OneDrive copy.
- **`n8n_workflow_v2_corrected.json`** → edit the **live workflow `yaBIrDOVbJTEMsH9`** in n8n via the **n8n MCP** (`n8n_update_partial_workflow`, surgical diff ops; run with `validateOnly:true` first), then regenerate this mirror from the live workflow (`n8n_get_workflow`). The JSON here is a mirror, not the source of truth. After editing, `n8n_validate_workflow` should report 0 errors; confirm a real command landed via the execution log (`n8n_executions`). See "n8n command handler" above before touching the Sheets/JotForm/Telegram nodes.
